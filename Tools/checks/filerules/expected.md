# File rules checks: the rules of `.editorconfig` on both faces

`commitfence rules list` and `rules show` list the rules the repository's `.editorconfig` sets for the compiler (the `dotnet_diagnostic.<id>.severity` lines), with a title from the installed SDK. `rules enable`, `disable`, `severity`, `set`, `remove` and `try` refuse on such a rule. The product never writes `.editorconfig`.

Every case runs on a folder this script makes under its scratch folder (a folder with an empty `commitfence.json` and the `.editorconfig` of the case), never on this repository's working folder. The repository's `.editorconfig` is only ever copied. Ids that the SDK does not know (`ZZ1001` and so on) are used where a case is about a comment, because for an id the SDK knows the SDK's title comes first.

What the real builds showed (a small project, a commit that declares `public class Bad` outside a namespace, the review run with `review --base HEAD~1 --head HEAD`; CA1050 reported on `Bad.cs`):

- A comment after the value (`# ...` or `; ...`, with or without a space before it) is not part of the value: `error # why` blocks, `warning # why` warns.
- Keys and words ignore case: `DOTNET_DIAGNOSTIC.ca1050.SEVERITY=Error` blocks, `= Warning` warns. A colon works as the separator. Spaces around the separator are allowed. A section name is case-sensitive (`[*.CS]` does not match `.cs` files). A property before the first section is ignored.
- `error` blocks (exit 1). `warning` and `suggestion` both warn (exit 0, printed as a warning: the review turns the compiler's note into a warning). `silent` and `none` print nothing. For a word the compiler does not know (`hidden`, `bogus`, an empty value) the compiler warns InvalidSeverityInAnalyzerConfig and the rule keeps its own default (CA1050 warns). The word `default` is a word of the compiler's, but the review of that tree ends incomplete (exit 2: its error log cannot be read); this is a finding about the review, not about the list, and is reported.
